While Tako does not strictly force you to use a specific folder structure, adopting a standardized layout helps keep your codebase clean, especially as it grows. The structure below is heavily inspired by modern web frameworks and is what we recommend for most applications.

## Recommended Structure

Here is a typical layout for a Tako application:

```text
my-tako-app/
├── commands/           # CLI Console commands
├── components/         # TUI Screens, Layouts, and UI widgets
├── config/             # YAML Configuration files
├── providers/          # Service Providers for dependency injection
├── services/           # Business logic and external API integrations
├── storage/            # Local SQLite databases, logs, and cache
├── go.mod
├── go.sum
└── main.go             # Application entry point
```

Let's break down the purpose of each directory.

### `commands/`

If you are building CLI tools alongside your TUI, this directory holds your console commands. Each file should represent a specific action the user can trigger via the terminal.

```go [commands/greet.go]
package commands

import "gettako.dev/tako/contracts"

type GreetCommand struct{}

func (c *GreetCommand) Signature() string {
	return "greet {name} {--s|shout : Print in uppercase}"
}

func (c *GreetCommand) Handle(ctx contracts.CommandContext) error {
	// ... logic here ...
	return nil
}
```

### `components/`

This is where the visual heart of your application lives. In Tako, a component is any struct that implements the `contracts.View` interface (which matches Bubble Tea's `Model`). 

You can organize this further by splitting it into:
* **Screens**: Full-page views that the router navigates between.
* **Layouts**: Shared wrappers (like a persistent sidebar or header) that wrap your screens.
* **Widgets**: Small, reusable UI elements like buttons or input fields.

### `config/`

Tako has a built-in configuration repository that reads `.yml` or `.yaml` files from this directory. You can organize your settings by feature, for example:
* `logging.yml`
* `database.yml`
* `theme.yml`

::note
By default, Tako looks for a `config` directory in the root of your project when it boots.
::

### `providers/`

Service Providers are the primary place where you bootstrap and register your application's dependencies into Tako's Service Container. If you need to initialize a database connection or register an event listener globally, you do it here.

```go [providers/app_provider.go]
package providers

import "gettako.dev/tako/contracts"

type AppProvider struct{}

// Register is where you bind things into the container
func (p *AppProvider) Register(app contracts.Application) {
	app.Singleton("db", func(c contracts.Container) any {
		return ConnectDatabase()
	})
}

// Boot is where you run logic after all providers are registered
func (p *AppProvider) Boot(app contracts.Application) {
	// ...
}
```

### `services/`

Keep your UI components clean by moving heavy business logic out of them. The `services/` directory is perfect for placing API clients, database wrappers, and core application logic. You can then inject these services into your components using the Service Container.

### `storage/`

Tako follows strict rules about where to write local files to keep the user's system clean.
* **Development**: Files are typically written to `.tako/` in your project root.
* **Production**: Files are written to a Virtual Home Folder (e.g., `~/.your-app-name/`).

You don't need to manually create this folder; use `app.Path().Storage()` in your code to automatically resolve the correct, safe location for logs, SQLite databases, and caches based on the current environment.

### `main.go`

Your `main.go` file should be kept as minimal as possible. Its only job is to instantiate the application, register your base Service Providers and routes, and call `tako.Run(app)`.
