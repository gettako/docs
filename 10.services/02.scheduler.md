The scheduler runs jobs in background goroutines and integrates their results with the Tako event bus. It tracks all active jobs and cancels them automatically on application
shutdown. This bridges Go's concurrency model with the TUI's sequential render loop — background work happens off the main thread, but results feed back into state and events that
drive re-renders.

## Dispatching a Job

```go [providers/orders/provider.go]
func (p *OrderProvider) Boot(app *foundation.Application) error {
    ctx := app.Context()
    job := ctx.Jobs().Dispatch(func(jobCtx context.Context) error {
        orders, err := p.api.FetchActive(jobCtx)
        if err != nil {
            return err // triggers OnError
        }
        ctx.State().Set("orders:active", orders)
        return nil // triggers OnSuccess
    })
    job.OnSuccess(func() {
        ctx.Emit("orders:loaded", nil)
    })
    job.OnError(func(err error) {
        ctx.Logger().Error("orders fetch failed", "err", err)
        ctx.State().Set("orders:error", err.Error())
    })
    return nil
}
```

`jobCtx` is cancelled when `CancelAll()` is called or when the application shuts down. Check `jobCtx.Done()` in any loop.

::warning
Don't block in `OnSuccess` or `OnError`. These run on the job's goroutine — use them only to emit events, set state, or log. Dispatch a follow-up job for async work.
::

## Periodic Jobs

```go [providers/notifications/provider.go]
func (p *NotificationProvider) Boot(app *foundation.Application) error {
    p.app = app
    ctx := app.Context()
    // Starts immediately, then repeats 30s after each completion
    ctx.Jobs().Every(30*time.Second, func(jobCtx context.Context) error {
        unread, err := p.api.GetUnreadCount(jobCtx)
        if err != nil {
            return err
        }
        ctx.State().Set("notifications:unread", unread)
        ctx.Emit("notifications:updated", unread)
        return nil
    })
    return nil
}

func (p *NotificationProvider) Shutdown() error {
    p.app.Jobs().CancelAll()
    return nil
}
```

`Every` uses post-execution timing — the next run starts 30s after the current one finishes. No overlap is possible.

::tip
Start with conservative intervals (30–60s) for API polling. Aggressive polling under 5s is rarely justified and adds measurable battery/CPU overhead.
::

## Cron Jobs

For applications that run continuously (as *daemons* or long-running TUIs), `Cron` lets you schedule tasks at **precise wall-clock times** using standard cron expressions — unlike
`Every`, which counts relative intervals from when the app started.

```go [providers/maintenance/provider.go]
func (p *MaintenanceProvider) Boot(app *foundation.Application) error {
    ctx := app.Context()

    // Rotate logs at midnight every day
    stop, err := ctx.Jobs().Cron("0 0 * * *", func() {
        ctx.Logger().Info("rotating logs")
        ctx.Emit("maintenance:log-rotate", nil)
    })
    if err != nil {
        return fmt.Errorf("invalid cron expression: %w", err)
    }
    p.stopCron = stop
    return nil
}

func (p *MaintenanceProvider) Shutdown() error {
    p.stopCron() // stop before app exits
    return nil
}
```

### Cron Expression Syntax

Tako uses standard 5-field cron expressions with **zero external dependencies**:

```
┌─────────── minute (0–59)
│ ┌─────────── hour (0–23)
│ │ ┌─────────── day of month (1–31)
│ │ │ ┌─────────── month (1–12)
│ │ │ │ ┌─────────── day of week (0–6, 0=Sunday)
│ │ │ │ │
* * * * *
```

| Expression      | Meaning                              |
|-----------------|--------------------------------------|
| `* * * * *`     | Every minute                         |
| `0 * * * *`     | Every hour, on the hour              |
| `0 0 * * *`     | Every day at midnight                |
| `*/5 * * * *`   | Every 5 minutes                      |
| `0 9 * * 1`     | Every Monday at 09:00                |
| `30 18 * * 1-5` | Weekdays at 18:30                    |
| `0 0 1 * *`     | First day of every month at midnight |
| `0 0 1 1 *`     | Every New Year's Day at midnight     |

Supported syntax: `*` (any), `n` (exact), `n,m` (list), `n-m` (range), `*/n` (step), `n-m/s` (range + step).

::tip
Unlike `Every`, `Cron` fires at **exact wall-clock times** regardless of when the app started. A cron job for `"0 0 * * *"` always fires at midnight — not 24 hours after boot.
::

::warning
The cron parser validates the expression at call time and returns an error immediately. Always check the returned `err` — a typo in the expression will silently never fire if you
ignore the error.
::

## Context-Aware Jobs

For jobs that make HTTP requests or do long-running I/O, always propagate `jobCtx`:

```go [providers/sync/provider.go]
func (p *SyncProvider) startSync(ctx *tako.Context) {
    job := ctx.Jobs().Dispatch(func(jobCtx context.Context) error {
        req, err := http.NewRequestWithContext(jobCtx, "GET", p.apiURL+"/inventory", nil)
        if err != nil {
            return err
        }

        resp, err := http.DefaultClient.Do(req)
        if err != nil {
            return err // Cancelled requests return context.Canceled
        }
        defer resp.Body.Unmount()

        var inventory []InventoryItem
        if err := json.NewDecoder(resp.Body).Decode(&inventory); err != nil {
            return err
        }

        ctx.State().Set("inventory:items", inventory)
        return nil
    })
    job.OnSuccess(func() {
        ctx.Emit("inventory:synced", ctx.State().Get("inventory:items"))
    })
}
```

## Scheduler Events

Subscribe from any provider to monitor job status:

| Event                     | Payload        | When                       |
|---------------------------|----------------|----------------------------|
| `scheduler:job:started`   | `JobID string` | Job begins execution       |
| `scheduler:job:completed` | `JobID string` | Job returns nil            |
| `scheduler:job:failed`    | `JobID, Error` | Job returns an error       |
| `scheduler:job:cancelled` | `JobID string` | Job's context is cancelled |
| `scheduler:all:cancelled` | `Count int`    | `CancelAll()` called       |

```go [providers/status/provider.go]
func (p *StatusProvider) Boot(app *foundation.Application) error {
    ctx := app.Context()
    ctx.Subscribe(ctx.Context, "scheduler:job:failed", func(e contracts.Event) {
        p.failureCount++
        ctx.State().Set("status:job_failures", p.failureCount)
    })
    return nil
}
```

## Using ctx.Spawn for Long-Lived Goroutines

For goroutines that run for the full provider lifetime (not just a job), prefer `ctx.Spawn`:

```go [providers/live_feed/provider.go]
func (p *LiveFeedProvider) Boot(app *foundation.Application) error {
    ctx := app.Context()
    // ctx.Spawn tracks the goroutine in the context's wait group
    // Shutdown waits for it to exit before proceeding
    ctx.Spawn(func(innerCtx context.Context) {
        ticker := time.NewTicker(5 * time.Second)
        defer ticker.Stop()

        for {
            select {
            case <-innerCtx.Done():
                return // Shutdown received
            case <-ticker.C:
                p.pollFeed(ctx)
            }
        }
    })
    return nil
}
```

**`ctx.Spawn` vs `ctx.Jobs().Dispatch`:**

|                                 | `ctx.Spawn`      | `ctx.Jobs().Dispatch`      |
|---------------------------------|------------------|----------------------------|
| Tracked by shutdown wait group  | ✅                | ✅                          |
| `OnSuccess`/`OnError` callbacks | ❌                | ✅                          |
| Best for                        | Long-lived loops | One-shot or repeated tasks |

::tip
For the initial data load in `Boot`, dispatch a one-shot job immediately and start the periodic `Every` job alongside it. Don't wait for the first `Every` tick — that could take 60
seconds. Users expect data to appear immediately, not after the first polling interval.
::
