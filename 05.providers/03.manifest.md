# Manifest & Dependencies

Not every provider should appear in `inspect`. **Service Providers** are internal implementations (database, config, router) built by the application developer and do *not* require
a manifest. They are intentionally hidden from public view. **Plugins**, on the other hand, are external extensions created by third-party developers. Plugins *must* implement a
manifest so they can be properly discovered and displayed by the public `go run . inspect` command.

Tako uses **duck-typing**: implement an optional interface and the framework recognizes you.

## HasManifest — Plugin Identity

```go
type HasManifest interface {
    Manifest() PluginManifest
}

type PluginManifest struct {
    Name        string
    Version     string
    Author      string
    Description string
    Repository  string
    License     string
}
```

### Example

```go
type AnalyticsPlugin struct{}

func (p *AnalyticsPlugin) Manifest() foundation.PluginManifest {
    return foundation.PluginManifest{
        Name:    "Tako Analytics",
        Version: "2.1.0",
        Author:  "Jane Doe <jane@example.com>",
        License: "MIT",
    }
}

func (p *AnalyticsPlugin) Register(app *foundation.Application) error { return nil }
func (p *AnalyticsPlugin) Boot(app *foundation.Application) error    { return nil }
```

### When to Use

| Scenario                                  | Requires Manifest? |
|-------------------------------------------|--------------------|
| Internal **Service Provider** (app logic) | ❌                  |
| Shared library across your org            | ✅                  |
| Published third-party **Plugin**          | ✅                  |
| Feature module in separate repo           | ✅                  |

**Rule: If it's an internal building block, it's a Service Provider. If someone else installs it as an extension, give it a Manifest to make it a Plugin.**

## DependsOn — Dependency Validation

```go
type DependsOn interface {
    Dependencies() []string
}
```

Declare which providers must be registered before yours boots:

```go
type PaymentPlugin struct{}

func (p *PaymentPlugin) Dependencies() []string {
    return []string{"DatabaseProvider"}
}
```

### How It Works

The framework **validates** before Boot — it does **NOT** auto-sort:

1. All `Register` calls complete
2. Framework checks every `DependsOn` declaration
3. Missing dependency → clear error, app does not start

```
provider *PaymentPlugin requires "DatabaseProvider" to be registered first
```

**Why validation, not sorting?** Sorting hides problems. Explicit ordering in `main.go` is self-documenting. Validation catches mistakes early.

### Custom Names

By default, the dependency name is the struct name. Override with:

```go
func (p *PaymentPlugin) Name() string { return "payment" }
```

## No Silent Registration

All providers live in `main.go`. No global registry, no `init()` discovery. If it's not listed, it doesn't run. You always know what's in your app.
